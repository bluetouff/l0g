In October, the FINOS foundation said Deutsche Bank, Goldman Sachs and several rivals were funding security fixes together. The alliance’s first set of updates covered [more than 50 projects](https://www.finos.org/press/major-banks-back-osera-open-source-security-standards-and-fixes) in the Java and Spring ecosystems. It makes sense from the perspective of a bank trying to keep an application running. If another institution relies on the same version of the same library, both may need the same patch. [S02](#source-S02)

On November 26, the Bank of England approached the problem from the other end. Its Financial Stability Report warned that a flaw in a widely used component could expose several firms at once. Paying for fixes together is one response to that common exposure. To see how it works, start one level below the applications customers use. [S01](#source-S01)

## The same library inside two banks

A payments application can rely on a library, a piece of prewritten code for a specific job, such as reading messages from another system. That library may call another component. The second link is a **transitive dependency**. A bank can end up relying on software it never selected separately, sometimes because the code came bundled inside a product bought from a vendor. [S01](#source-S01) [S03](#source-S03)

<OssFinanceFigure lang="en" kind="dependencies" />

Two banks can buy from different vendors and end up using the same library in their applications. In 2024, researchers discovered compromised versions of XZ Utils, a routine compression tool. The episode showed how an ordinary piece of software could become an entry point. The [CERT-EU alert](https://www.cert.europa.eu/publications/security-advisories/2024-032/) covers the compromised software. For a bank, the consequences would depend on which versions were running, the functions they supported and the safeguards in place. [S07](#source-S07)

The financial system can come under strain when several firms lose functions that are difficult to replace at the same time. Imagine a disruption that delays payments to several businesses. Companies counting on the money to pay suppliers may have to find cash that day. A backup offers less protection when it relies on the same component that just failed. That logic also applies to oversight of [shared technology providers](/en/analysis/invisible-suppliers-european-banking-risk/). [S01](#source-S01) [S08](#source-S08)

## Copying the code is cheap. Maintaining it takes work

Open-source licences let competing businesses reuse the same software. The benefit is tangible when a company avoids doing the work from scratch. In a [FINOS and Linux Foundation survey](https://www.linuxfoundation.org/hubfs/Research%20Reports/StateofOpenSourceinFinancialServices_2026_Report_110226.pdf?hsLang=en), **47% of the 215 people who answered the question** reported estimated annual savings of at least $5 million from open source. One in five said they did not know. The respondents came from finance and related organisations, and reported their own estimates. [S05](#source-S05)

<OssFinanceFigure lang="en" kind="survey" />

A [Harvard Business School working paper](https://www.hbs.edu/ris/Publication%20Files/24-038_51f8444f-502c-4139-8bf2-56eb4b65c58a.pdf) approaches the value from another direction. If each component under study were rebuilt once, the authors estimate the cost at $4.15 billion. If each company had to rebuild the code it relies on in-house, the estimate rises to $8.8 trillion. Those scenarios model the cost of **recreating** widely reused software across the economy. The survey figures measure annual savings as estimated by respondents. [S04](#source-S04) [S05](#source-S05)

Downloading a library still leaves someone responsible for maintaining it. When a bank pays an engineer to fix a flaw, other users can benefit from the work. Every user wants a fix to exist, and each has a reason to wait for somebody else to pay. Companies are already assigning employees and contractors to open-source projects. In the quantifiable responses to an [open-source funding survey](https://opensourcefundingsurvey2024.com/), their labour accounted for **86%** of the reported value contributed. Direct financial contributions made up the rest. [S06](#source-S06)

## Banks split the cost of a fix

The FINOS alliance is called **OSERA**. Suppose two banks depend on an older release of a Java library. A patch is available for the newer release. Moving the whole application onto it can take time, since the bank has to check compatibility with the software around it. Both institutions could pay separately to adapt that fix to the older release. OSERA arranges for them to share the work. This kind of adaptation is called a **backport**. [S02](#source-S02) [S12](#source-S12)

<OssFinanceFigure lang="en" kind="osera" />

A bank gets a release it can verify and test on its own systems. It still has to decide where and when to install it. The shared service becomes a dependency of its own. A workable fallback includes being able to check where a patch came from and rebuild packages from source. The immediate saving comes from doing the work once. The benefit for financial stability depends on how banks actually roll out the fixes. [S01](#source-S01) [S08](#source-S08) [S12](#source-S12)

## From a software inventory to a fallback plan

In Europe, the ordinary ICT risk management framework under [DORA](/en/glossary/dora/) requires financial firms to track third-party libraries, including open-source libraries, in services that support critical or important functions. Its technical rules require automated vulnerability scanning and assessment at least weekly for the ICT assets behind those functions. A list of components, often known as a **software bill of materials** or **SBOM**, helps teams locate the affected software. When an alert lands, they also need to know which versions are running and who can intervene. [S09](#source-S09)

The [Cyber Resilience Act](/en/analysis/cyber-resilience-act-vulnerability-reporting/) approaches the issue from the product side. Under the [regulation’s timetable](https://eur-lex.europa.eu/eli/reg/2024/2847/oj), manufacturers in scope have had to report certain incidents and actively exploited vulnerabilities since September 11, 2026. The main security obligations and the tailored regime for open-source software stewards apply from December 11, 2027. DORA remains the starting point for a bank managing the risks of the software it uses. [S09](#source-S09) [S10](#source-S10)

The risk committee can ask a plain question. If a shared library stops working tomorrow, which operations carry on, and who can get the others back online? Public documents show how the risk arises and how some institutions are responding. Answering for individual banks would take inventories of the versions in use and the fallback plans. That is where the value of a fix, and of the time saved installing it, becomes concrete. [S01](#source-S01) [S08](#source-S08)
